I Audited 1.31M LLM Tokens. Here's Where Your AI Bill Actually Goes.

Kinet Engineering · Part of the 4-engine benchmark series · 6 min read

Most "why is my API bill so high" advice stops at "turn down max_tokens". That's not where the money is. We instrumented every single API call across four AI coding agents running the same real-world task — and the bill has a very specific shape.

The headline: across 1,310,000 audited tokens and 341 turns, 7.5% of API calls consumed 63% of the entire budget. The worst single call cost 190K tokens.

The task, briefly

A 6-sheet medical CRM workbook, several hundred thousand rows. Cross-tabulate downtime/installation data by hospital tier and time window; produce a dark-theme interactive ECharts report. Same task, same model tier, four different agent harnesses. Full scoring in the benchmark article; this post is only about cost.

Anatomy of a 190K-token call

The most expensive single call in the audit happened like this:

  • An agent needed data from a workbook exported as a 16-part text dump.
  • No file-reading tool — so it shelled out to Bash and cat the parts sequentially, one per turn.
  • Each turn re-sent the entire conversation history plus everything read so far.
  • By part 16, every call was carrying a ~190K-token payload. Sixteen times.

Nothing about this is a model problem. The model did what it was told. The harness simply had no native way to touch a big file, and "no tool" silently converts into "burn the context window."

Three context strategies, one winner

  • Truncation (drop old turns): cheap, but the agent forgets its own plan and loops. We watched loops cost more than the memory they saved.
  • Compression (summarize old turns/tables): fine for prose, lossy for tables. This is what sank V2 — summarized rows became invented rows.
  • Never load it at all: keep the data on disk behind tools (read_range, filter, aggregate) and pass only results. This is the only strategy that scales, and it's boring engineering, not a clever prompt.

The 60-second self-audit

Open your agent's logs (or your provider dashboard) and check four things:

  1. Payload distribution: sort calls by tokens. If your p95 is more than ~5× your median, something is re-sending history. (Our 7.5%/63% finding is exactly this shape.)
  2. File contents in context: search transcripts for raw data rows. If the model ever "reads" a whole file into the conversation, you're paying compound interest on it every turn.
  3. Cost visibility: if your tool shows conversations but not cost per conversation, you will find out from the invoice instead.
  4. Detour count: count Bash/python round-trips per task. Each one is a context tax paid at full history length.

What to do about it

Not "use a smaller model" — the model was constant across our whole benchmark and the cost still varied 3×. The bill is architecture:

  • Native tooling for your dominant data type (for us: SAX-streaming xlsx readers, CSV filters — the file streams through, never sits in context).
  • Tool outputs capped at result-size, not raw-size.
  • A cost meter next to the conversation, live. Watching a 190K call happen is the only reliable way to care.
